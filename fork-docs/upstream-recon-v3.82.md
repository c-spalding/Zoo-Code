## 5. Surprises and risks

1. **Tag `v3.82.0` is not an ancestor of `zoo/main`.** The release tag was cut from a
   different history shape (likely a release-automation branch) than the one that landed
   on `main`. Both converge to byte-identical trees at the version-bump point, but anyone
   doing ref-based work (e.g. `git describe`, `git log --first-parent`) should use the
   `main`-line commit `0dbd5846f` as the canonical v3.82.0 point-in-history, not the tag,
   if they need ancestry-based reasoning (cherry-pick base-commit selection, `git log
-L`, etc). Using the tag itself for content inspection (`git show TAG:path`) is fine
   since the trees match.
2. **Upstream independently built adaptive-thinking / "max" effort support** (feature #9)
   using a different, more hardcoded model-id-matching strategy than the fork's exported
   constant. This is the single highest-conflict-risk tranche: it is not a clean
   superseded-vs-absent case, it is a genuine parallel-invention collision that needs a
   deliberate reconciliation decision (which model-id list wins, or do we merge both).
3. **`MaxOutputTokensControl` is a name collision, not a feature collision** (feature #2).
   Upstream has a same-named component doing something unrelated (generic max-tokens
   slider for GLM-style `supportsMaxTokens` models). The fork's Bedrock-probe-specific
   logic is still absent, but re-applying naively would either clobber the upstream
   component or require renaming the fork's component to avoid confusion.
4. **Upstream's ModelPicker fix (feature #14) is more advanced than the fork's own
   change**, which appears to have been an incomplete/abandoned attempt (only the
   `automaticFetch` string is touched in the fork, no `staticModelList` counterpart was
   ever added there). Re-applying the fork's diff here would be a strict regression.
5. **The kimi-k2-thinking model key correction** (`moonshot.` -> `moonshotai.`, feature
   #10) looks like a genuine unshipped upstream bug fix hiding inside an otherwise
   superseded tranche. Worth flagging as a standalone, low-risk, high-value patch
   candidate (and possibly worth upstreaming directly via PR rather than just keeping it
